Source: `.superpowers/sdd/2026-09-07-m1a-static-pipeline/task-22-report.md` (Task 22,
section "Smoke test: measured time and memory"); the numbers were not re-measured in Task 23 — only
quoted, as the controller instructed (re-measuring would have cost a full `cargo test`;
the closing session had no cheap step for it). The owner's machine, `/usr/bin/time -l`, fixture —
a 1,000,049-byte document (`<!doctype html><body>` + a repeated `<div><p>lorem ipsum

## Deep nesting: debug vs release (debt D2.a, 2026-09-28)

Fixture — a single chain with no siblings: `<body style="margin:0">` + D × `<div
style="margin-top:1px">` + `x` + D × `</div>` + `</body>`, the string is generated iteratively.
Stages were measured separately with a throwaway `examples/` binary (not committed: CI cannot run a
release-only benchmark, so the numbers are what gets committed): `cl_html::parse_document_str` →
`StyleEngine::resolve` → `cl_layout::build` (box tree) → `cl_layout::layout` (in the table —
minus the box tree, which `layout` builds itself). Debug — median of 3 runs, release
(`--release`: `lto = "thin"`, `codegen-units = 1`) — median of 5. The owner's machine (Apple
Silicon, 8 cores), HEAD `2efe0e8`.

**Debug** (what `cargo nextest` runs):

| Depth | parse | style resolve | box tree | layout |
|---|---|---|---|---|
| 2 000 | 172 ms | 161 ms | 2.8 ms | 3.0 ms |
| 4 000 | 662 ms | 552 ms | 5.7 ms | 5.1 ms |
| 8 000 | 2 605 ms | 2 055 ms | 12.3 ms | 10.3 ms |
| 16 000 | 10 451 ms | 7 878 ms | 23.2 ms | 18.0 ms |

**Release:**

| Depth | parse | style resolve | box tree | layout |
|---|---|---|---|---|
| 2 000 | 10.0 ms | 2.0 ms | 0.4 ms | 0.4 ms |
| 4 000 | 34.1 ms | 4.2 ms | 0.8 ms | 0.7 ms |
| 8 000 | 142.6 ms | 8.4 ms | 1.4 ms | 1.6 ms |
| 16 000 | 531.2 ms | 16.5 ms | 3.2 ms | 3.3 ms |
| 32 000 | 2 068.7 ms | 35.1 ms | 6.7 ms | 9.2 ms |

Conclusion:

- **Style resolve is linear in release** — every doubling of depth ≈ ×2 (2.0 → 4.2 → 8.4 → 16.5 →
  35.1 ms). The quadratic behaviour of the debug profile (×3.4–3.8 per doubling) is a debug check of
  stylo itself: `StyleBloom::assert_complete` (`stylo-0.20.0/bloom.rs`, only under
  `debug_assertions`) walks the whole ancestor chain on every element. `sample` (macOS) on a
  debug run at depth 16 000: 2 633 of 2 764 `StyleEngine::resolve` samples (95%) are inside
  `assert_complete`. `cl-style` has no O(depth)-per-node code of its own; no code changed.
- **Box tree and layout are linear in both profiles.**
- **Parse is not linear in release either** (×3.4–4 per doubling; 2.07 s at depth 32 000). `sample` at
  depth 64 000: 3 066 of 3 073 samples are in html5ever's
  `TreeBuilder::close_p_element_in_button_scope` → `in_scope`. Every `<div>` start tag in
  the "in body" mode checks "has a p element in button scope" per HTML §13.2.6.4.7, `<div>`
  is not a scope boundary, and the check walks the whole stack of open elements — O(depth) per tag. This
  is html5ever code, not ours, and outside the D2 mandate (only `cl-style`/`cl-layout`); left as an open
  debt (MEMORY.md, M1a debt 1). A known mitigation is a tree-depth cap in the parser,
  as in Blink (`HTMLConstructionSite`, 512 levels) — a separate task with an ADR.

## Many inlines in one paragraph (debt D2.b, 2026-09-28)

A `<p>` of N × `<span>a</span>` (one line, N glyphs). `span_item`
(`crates/layout/src/text.rs`) looked up a cluster's span with a linear scan and was called for every
cluster, i.e. O(clusters × spans); now it is a binary search (`partition_point`), O(log
spans). Time of `cl_layout::layout` without the box tree; the same throwaway binary and method as in
D2.a.

| N | debug before | debug after | release before | release after |
|---|---|---|---|---|
| 10 000 | 220 ms | 78 ms | 28.8 ms | 6.3 ms |
| 20 000 | 747 ms | 156 ms | 99.6 ms | 13.0 ms |
| 40 000 | 2 665 ms | 311 ms | 371.1 ms | 26.8 ms |
| 80 000 | — | — | 1 028.9 ms | 58.3 ms |

Before — ×3.4–3.7 per doubling (the quadratic term dominates already from 20 000), after — ×2.
The regression test `many_inline_spans_should_lay_out_in_linear_time`
(`crates/layout/tests/inline.rs`, 10 000 spans, budget 5 s / 15 s under `CL_SMOKE_SLOW=1`)
also passed on the old code (~0.22 s in debug): at that N the quadratic behaviour shows only in the growth,
not against the threshold.

## A wide sibling list and `:nth-*`/`~` (debt D2.c, 2026-09-28)

`<body><div>` + N × `<p></p>\n` (siblings separated by whitespace text nodes, as in
any hand-written page), one author selector. `ElementHandle::{prev,next}_sibling_element`
/ `first_element_child` (`crates/style/src/handle.rs`) walked the sibling list, skipping
non-elements; now the links to the nearest elements are computed once per pass in
`NodeArena::link` (O(n), `Cell` fields in `NodeSlot`, zero `unsafe`, the handle is still one
word) and each step is one `Cell` read. Time of `StyleEngine::resolve`; the same throwaway
binary, debug — 1 run, release — median of 5.

| Selector | N | debug before | debug after | release before | release after |
|---|---|---|---|---|---|
| `p:nth-child(2n+1)` | 5 000 | 1 157 ms | 146 ms | 1.2 ms | 1.3 ms |
| | 10 000 | 3 970 ms | 517 ms | 2.7 ms | 2.4 ms |
| | 20 000 | 20 059 ms | 1 946 ms | 5.5 ms | 4.9 ms |
| | 40 000 | — | — | 11.3 ms | 11.7 ms |
| `p:nth-last-child(2n+1)` | 5 000 | 906 ms | 143 ms | 1.2 ms | 1.2 ms |
| | 10 000 | 4 289 ms | 504 ms | 2.5 ms | 2.5 ms |
| | 20 000 | 16 907 ms | 1 895 ms | 5.4 ms | 5.2 ms |
| | 40 000 | — | — | 11.0 ms | 11.2 ms |
| `.nomatch ~ p` | 5 000 | 3 296 ms | 1 428 ms | 148.0 ms | 81.3 ms |
| | 10 000 | 12 108 ms | 5 636 ms | 580.0 ms | 325.6 ms |
| | 20 000 | 44 969 ms | 22 750 ms | 2 332.9 ms | 1 300.5 ms |
| | 40 000 | — | — | 10 085.8 ms | 5 282.1 ms |

What this means:

- **`:nth-child`/`:nth-last-child` are linear in release both before and after.** `selectors` caches
  the indices (`NthIndexCache` in stylo's thread-local `SelectorCaches`, alive for the whole traversal), so
  every element takes O(1) steps to an already-computed neighbour. Debug is quadratic even after the
  fix: `matches_generic_nth_child` (`selectors-0.40.0/matching.rs`) under `debug_assert_eq!`
  recomputes the index **without** the cache — O(position) steps per element; `sample` on a debug run at
  N = 40 000: 2 007 of 2 057 traversal samples are in `nth_child_index`. The fix removed our walk over
  text nodes from each such step: debug is ×7.9–10.3 faster, and the regression test
  `nth_child_over_twenty_thousand_siblings_should_resolve_under_the_time_bound`
  (`crates/style/tests/sibling_selectors.rs`, 20 000 children, budget 5 s) went from red (13.8 s)
  to green (~2.0 s).
- **A non-matching `~` stays quadratic in release too** — that is the `selectors` algorithm
  (for every element, walk all previous siblings, no cache; Gecko/Blink/WebKit do the
  same). The fix made each step cheaper (release ×1.8–1.9) but did not change the class: 40 000 siblings —
  5.3 s. An open DoS vector, recorded in MEMORY.md (M1a debt 1); the cure is not in `cl-style` but
  a cap on document width/size or a time budget for the style pass.
- Memory: `NodeSlot` 40 → 64 bytes (three `Cell<Option<&NodeSlot>>`), +24 bytes per node per style
  pass plus a reused buffer for the widest child list (16 bytes per child).
  Peak RSS (`/usr/bin/time -l`, release, 3 runs): N = 40 000 `nth` 24.8 → 26.5 MiB;
  depth 16 000 49.4 → 48.0 MiB (within allocator noise — the expected +0.8 MB is smaller than the
  spread between binaries); 40 000 spans 117.6 → 117.6 MiB.
